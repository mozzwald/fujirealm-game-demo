# Atari 8-bit Memory Layout

This document describes the Atari client memory layout, based on:

- [`atari8-client/fujirealm.asm`](../atari8-client/fujirealm.asm)
- `atari8-client/build/fujirealm_game.lab` (generated by `make -C atari8-client`)
- `atari8-client/netstream/NSENGINE.lab` (generated by the same build)

All addresses are hexadecimal. Sizes are shown in both bytes and approximate  
KiB where useful.

## Summary

- Assembled game payload from `fujirealm.asm`:  
`20,238` bytes (`build/fujirealm_game.xex`)
- Bundled Netstream handler payload:  
`1,224` bytes (`netstream/NSENGINE.OBX`)
- Combined shipped client payload:  
`21,699` bytes (`fujirealm.xex`, 12-player Wilhelm-animation build)
- Runtime client-owned RAM span:  
roughly `$2000-$9FF3` (`32,756` bytes, about `32.0 KiB`)

The runtime footprint is larger than the XEX file because the client reserves  
fixed screen pages, world/cache pages, font pages, scratch buffers, and code  
segments across a broad address range.

## Major Fixed Buffers

### Display

- `SCREEN = $4680`
- `SCREEN_BACK = $4A40`
- Each screen page is `40 * 24 = 960` bytes
- Total reserved screen memory: `1,920` bytes

The viewport uses `40x20` character cells for the game view plus HUD/separator  
rows inside the same screen pages.

### Fonts

- `FONT = $5000`
- The active shared font page is `1,024` bytes

The overworld and cave share the `$5000` font and logical mapping. The former  
`$7C00` cave-font page was reclaimed for the paged dialogue modal.

## Logical Art and Renderer Budget

- The four active logical tables begin at `$4F00`, contain 52 entries each,  
and end at `$4FCF`; 48 bytes remain before `FONT=$5000`.
- The high-memory overworld copy begins at `$8030`. Cave table labels alias  
that identical mapping instead of storing a second 204-byte copy.
- The default build's main block ends at `$4674`, leaving 11 bytes before the  
front screen at `$4680`.
- The high client block ends at `$8B8F`, leaving 112 bytes before fixed  
scratch RAM at `$8C00`.
- Both the default three-player build and a 12-player stress build pass all  
assembly ownership guards.

Slime and bat frames are logical-table entries only; they do not add a second  
font page. Projectile rendering reads the Bullet entry's upper pair and never  
addresses a lower screen row.

### World / Terrain Cache

- `WORLD = $6000` (rows stored two per page: pages `$60-$6B`)
- `WORLD_PENDING = $7000` (pages `$70-$7B`)
- The `$6C00-$6FFF` gap between the caches hosts the  
realtime v3 engine: CRC-16 nibble tables, in-place COBS decode/encode, the frame  
validator/dispatcher, TX finalization, cache-step ACK, and the  
CLIENT_NET_STATS sender.  The bounded handler receive pump in  
block is guarded by `ert *>WORLD_PENDING`. Retiring the  
v2 magic-scan parser also removed the `net_rt_checksum_offset` byte that  
aliased `LOGIN_STATE_BUFFER+0` at `$8CD0`.

Nominal world dimensions are:

- `WORLD_W = 128`
- `WORLD_H = 96`

Realtime window dimensions are:

- `NET_WINDOW_W = 32`
- `NET_WINDOW_H = 24`

The client uses two cache regions so terrain/window updates can be staged  
without corrupting the currently active view.

## Bounded Realtime Receive Pump

Moves receive-loop work out of the main `$2000` segment and into the  
realtime v3 block:

- `NET_RX_BUDGET_REMAINING = $6C4D`
- `NET_RX_DELIMITERS_REMAINING = $6C4E`
- `NETSTREAM_RECV_REALTIME_PACKETS_BOUNDED = $6C56-$6C94` (63 bytes)
- complete realtime v3 block ends at `$6F36`
- next free byte is `$6F37`, leaving 201 bytes before `$7000`

Each invocation processes at most 64 handler bytes or four COBS delimiters.  
Parser state remains in the existing fixed realtime state buffer, so an  
encoded frame may span video frames without being discarded. Normal gameplay  
uses one receive budget before controls; modal/blocking service retains one  
bounded receive pass through `netstream_service_realtime_io`.

The main block now ends at `$460E` in both the default and 12-player builds,  
leaving 113 bytes before `SCREEN=$4680`. The default `$5400` state block ends  
at `$5597`; the 12-player stress build ends at `$55E8`, leaving 23 bytes.

## Remote Shot Visuals

Distributes cosmetic remote-tracer state and code across guarded  
regions:

- `UPDATE_REMOTE_BULLETS = $3154`; the next routine begins at `$323F`, so the  
indexed update loop occupies 235 bytes in the main segment.
- In the default 3-player build, tracer tables occupy `$557D-$5597` (27  
bytes). In the verified 12-player stress build they occupy `$55C5-$55E8`  
(36 bytes), leaving 23 bytes before the `$5600` guard.
- `NETSTREAM_APPLY_REMOTE_PLAYERS = $5A00`,  
`SPAWN_REMOTE_BULLET = $5AB4`, `REMOTE_BULLET_HITS_TERRAIN = $5B1B`, and  
`CLEAR_REMOTE_BULLETS = $5B48`. The complete `$5A00` block ends at `$5FFF`;  
there is no free byte before `WORLD = $6000`.
- `DRAW_REMOTE_BULLETS = $8BAF-$8BED` uses the final 63-byte helper slot in  
the high client block, leaving 18 bytes before the `$8C00` scratch area.

The default and `REMOTE_PLAYER_SLOTS=12` builds both pass the  
`ert *>SCREEN`, `ert *>$5600`, `ert *>WORLD`, `ert *>APPKEY_DATA_BUFFER`,  
`ert *>$A000`, and `ert *>$C000` ownership guards. In the 12-player build the main segment ends  
at `$460E`, leaving 113 bytes before `SCREEN = $4680`.

## Network / Login / Scratch Area

The main fixed scratch area begins at `$8C00` and holds:

- AppKey buffers
- Login request/response buffers
- Username/token/server-host strings
- Realtime receive/transmit packet buffers
- Realtime parser/watchdog state

Important anchors from the current build:

- `APPKEY_DATA_BUFFER = $8C00`
- `LOGIN_PKT_BUFFER = $8C48`
- `USERNAME_BUFFER = $8C70`
- `TOKEN_BUFFER = $8C90`
- `N_DEVICESPEC_BUFFER = $8D00`
- `SERVER_HOST_BUFFER = $8E00`
- `NET_REALTIME_PACKET_BUFFER = $8E80`
- `NET_REALTIME_TX_PACKET_BUFFER = $8EC0`
- `NET_PACKET_PAYLOAD_BUFFER = $8F00`

## Netstream Handler

The MADS Netstream handler is relocated to `$9000`:

- `NETSTREAM_HANDLER_BASE = $9000`
- Handler runtime span from `NSENGINE.lab`:  
`$9000-$999C`
- Runtime reserved size:  
`2,461` bytes

This keeps the handler out of the main client code and cache regions while  
still shipping inside the combined `fujirealm.xex`.

## High Helper / Sound Effects Block

The high helper block lives at `$9A00`:

- `SFX_CODE = $9A00`
- `DRAW_HUD_PVP_KILLS = $9A00`
- `HUD_DRAW_FOUR_DIGITS = $9A0E`
- `NETSTREAM_CYCLE_BAUD = $9ACB`
- `NETSTREAM_STORE_PENDING_WINDOW_ROW = $9C74`
- `SFX_UPDATE = $9D84`
- Current last exported label:  
`SFX_MESSAGE_MAP = $9F5E`
- Current last byte used:  
`$9FF3`
- Next free byte: `$9FF4` (12 bytes before `$A000`)

This region contains the PvP kill HUD helpers, baud selector, bootstrap  
retry/reset helpers, parser validation/resync helpers, SFX update/request code,  
and note/control tables for the client-side sound effect system. The block is  
guarded with `ert *>$A000` so it cannot silently grow into the PMG area below.

## Player/Missile Graphics Area (`$A000-$BFFF`)

`$A000-$BFFF` is RAM with BASIC disabled, which is how MyPicoDOS boots the
game, and nothing else in the client uses it — the next segment down ends at
`$9FF3`. The PMG build (`PMG_PLAYER=1`, the default) puts everything for the
local player's Player/Missile sprite here, so it costs nothing from the very
tight `$2000-$9FFF` map:

| Range         | Use                                                              |
| ------------- | ---------------------------------------------------------------- |
| `$A000-$A2FF` | Unused PM area, zeroed once by `pm_init`                         |
| `$A300-$A3FF` | Missiles — M0 is the local bullet, M1-M3 the remote tracers       |
| `$A400-$A7FF` | P0-P3, 256 bytes each (single-line resolution)                   |
| `$A800-$AC80` | PMG code, sprite colors, and the six 24-row PM frames            |
| `$AC81-$BFFF` | Free                                                             |

`PMBASE = $A0`; single-line resolution requires the 2 KB alignment. The block
is guarded with `ert *>$C000`. Building with `PMG_PLAYER=0` omits the segment
entirely and restores the 2x2 character sprite, so the flag is a working
bisect point if PMG is ever suspected.

PM sprites are not part of the playfield, so swapping the display list does
not take them off screen on its own. `apply_display_now` calls
`pm_set_display`, which shows the sprite and missiles only while
`display_list_game` is up and clears them out of PM RAM otherwise — that one
hook covers every modal, the title screen, the netstream screen and the
connection-failed screen, and any modal added later. `pm_sync_hw` sets
`GRACTL` from `pm_shown` rather than unconditionally on, because the modals
call `set_text_palette` *after* switching display lists and would otherwise
turn the sprite straight back on.

Because `CRITIC = 1` suppresses the OS stage-2 VBI (see the `CRITIC` note in
`fujirealm.asm`), no OS shadow is ever copied to hardware. `pm_sync_hw` writes
`DMACTL`, `GRACTL`, `PRIOR`, `COLPM0`/`COLPM1` and the size/position registers
directly, the same way `sync_colors_hw` handles the playfield colors. Writing
`SDMCTL`/`GPRIOR`/`PCOLRn` alone silently does nothing during realtime play.

### Checking the sprite's vertical position

`PM_PLAYFIELD_TOP` is the PM RAM byte index of the playfield's first scanline:
8 scanlines of vertical blank before display list DMA starts, plus the three
blank-8 lines the game display list opens with, so `8+24`. In single-line
resolution one byte index is one scanline, so if the sprite sits high or low
by a fixed amount this constant is the thing to adjust. To read the current
position back out of a running client, dump `$A400` (P0) and `$A500` (P1) with
`atari_dump_memory` — the sprite is the only non-zero 24-byte window in each.

## Practical Reading

For client work, the most important boundaries are:

- `$2000-$467F`: main gameplay code budget
- `$4680-$4DFF`: screen buffers, must not be overrun
- `$5000-$53FF` and `$7C00-$7FFF`: font/tile memory
- `$6000-$7BFF`: terrain cache pages
- `$8C00-$8FFF`: login/network scratch state
- `$9000-$999C`: Netstream handler
- `$9A00-$9FFF`: guarded PvP/baud/bootstrap/window-row/SFX/shot-step block, currently used through `$9FF3`
- `$A000-$BFFF`: PM RAM plus the PMG code/art block, the one place with real room left

If the client grows further, the tightest ownership boundaries to watch are the  
main `$2000` segment below `SCREEN`, the `$8C00-$8FFF` scratch area, and the  
space above the Netstream handler/SFX block.
